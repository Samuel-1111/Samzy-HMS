## Application environment

Set these values in local `.env.local` and the Vercel project:

- `SUPABASE_URL` — the Supabase Project URL. Used by trusted server-side code.
- `NEXT_PUBLIC_SUPABASE_URL` — the exact same Project URL. Required by browser and SSR clients because browser code cannot read server-only environment variables.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — the project's publishable key. This is designed for browser use; database access must still be protected by RLS.
- `SUPABASE_SECRET_KEY` — server-only secret key used by trusted server-side account provisioning and privileged database operations. Never prefix it with `NEXT_PUBLIC_`, expose it to browser code, or commit its value.

The two URL variables must contain the same URL. The server-side admin client reads `SUPABASE_URL` first and retains `NEXT_PUBLIC_SUPABASE_URL` as a compatibility fallback.

## Application authentication

Portal sign-in credentials are configured separately in Vercel environment variables. The Supabase secret key is not a portal username or password and does not replace the portal credential variables.

## Bootstrap and tenant setup

- `HMS_BOOTSTRAP_TOKEN` — a random secret generated by the operator, at least 32 characters long. It is not supplied by Supabase. Keep it private and configure it only in Vercel.
- The one-time bootstrap endpoint uses this token to authorize creation of the first hospital tenant and initial administrator.
- `HMS_HOSPITAL_ID` — do not invent this value. Set it only after a successful, authorized bootstrap returns the hospital UUID.

Bootstrap is one-time and will refuse to create another tenant if a hospital row already exists. Confirm the legal hospital identity and authorization before running it.

## Security

Never put `SUPABASE_SECRET_KEY`, `HMS_BOOTSTRAP_TOKEN`, or portal passwords in GitHub, frontend code, screenshots, or chat. Store them in Vercel Project Settings → Environment Variables or an approved password manager. Only the URL and publishable key may be exposed to browser code.

## Health endpoint

`GET /api/health/supabase` performs a non-mutating request against the published-content API to verify that the configured endpoint is reachable. It does not prove Auth, RLS role claims, private Storage, or clinical workflows are ready.
